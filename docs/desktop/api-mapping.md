# Smart Space Desktop — API Mapping (Phase 0 Audit)

Source: `src/backend_engine` (FastAPI, application version `0.1.0`).
Everything below is confirmed by the code; no assumptions were added. Missing capabilities are listed in the “Gaps” section.

## 1. General Information

| Parameter | Value |
|---|---|
| API prefix | `/api/v1` |
| Authorization | `Authorization: Bearer <token>`; tokens use the `ss_…` format and are stored on the server as a SHA-256 hash (`api_token`), with `expires_at` and `revoked_at` support |
| Roles | `admin`, `user`, `viewer`, `gateway` |
| Token issuance or login endpoint | **Missing** — users enter the token manually in Settings |
| “Who am I” endpoint (`/me`) | **Missing** — the client does not know the role and must rely on 403 responses |
| WebSocket / SSE | **Missing** — there is only an internal in-process `EventBus` |
| Error format | `{"detail": "<string>"}`; FastAPI validation errors (422) use an array for `detail` |
| Dispatcher in `app.py` | `FakeDispatcher` — commands **do not reach real devices** (MQTT gateway is not connected) |

### Role Permissions

| Role | Permissions |
|---|---|
| admin | all |
| user | device:read/write, command:create/read/confirm |
| viewer | device:read only |
| gateway | device:read, device:report |

Consequences: `viewer` cannot read commands; `user` cannot delete devices or trigger emergency stop.

### Schemas

**CreateDeviceDto** (`extra=forbid`): `slug` (`^[a-z0-9_]{3,64}$`), `name` (1–100), `type`, optional `room_id` (UUID), `capabilities: string[]` (≤32).

**DeviceDto**: `id`, `slug`, `name`, `type`, `room_id|null`, `enabled`, `availability` (`online|offline|unknown`), `capabilities[]`, `state{}` (arbitrary object), `firmware_version|null`, `last_seen_at|null`.

`type` enum: `temperature_sensor, humidity_sensor, motion_sensor, light_sensor, door_sensor, window_sensor, smart_light, smart_relay, smart_plug, smart_speaker, custom`. Unknown UI values should be rendered as `custom` or the raw string, not cause a crash.

**SubmitCommandDto** (`extra=forbid`): `command_id` (UUID generated by the client and used as the idempotency key), `action`, `parameters{}`, `source` (defaults to `"api"`). Desktop always sends `source="api"`.

**CommandDto**: `id`, `command_id`, `device_id`, `action`, `parameters{}`, `status`, `source`, `requested_by`, `decision_reasons[]`, `correlation_id|null`, `created_at`, `updated_at`, `expires_at|null`, `dispatched_at|null`, `acked_at|null`.

### Command Statuses (wire values are lowercase)

`pending, approved, rejected, awaiting_confirmation, expired, cancelled, dispatched, acknowledged, failed, timed_out`

Transitions: `pending → approved | rejected | awaiting_confirmation`; `awaiting_confirmation → approved | rejected | expired | cancelled`; `approved → dispatched | cancelled`; `dispatched → acknowledged | failed | timed_out`.
Terminal: `rejected, expired, cancelled, acknowledged, failed, timed_out`.
Execution is considered successful **only** when the status is `acknowledged`.

### Safety Engine: Client Visibility

- Verdicts (`approve/reject/confirm`) are not returned separately. The client sees them through `status` (`approved` / `rejected` / `awaiting_confirmation`) and `decision_reasons`.
- Known reasons: `emergency_stop_active, device_not_found, device_disabled, device_offline, unknown_action, unsupported_action, invalid_parameters, risky_action, automated_confirmation_not_allowed, rate_limit_exceeded, conflicting_command_active`. Unknown reasons are shown as raw strings.
- Known actions (`ACTIONS`): `turn_on`, `turn_off` (capability `on_off`), `set_brightness` (capability `brightness`, `{"brightness": int 0..100}`, strict integer).
- Confirmation is required for `turn_on` on `smart_relay` / `smart_plug`. The confirmation window is 60 seconds (`expires_at`).
- Available device commands are derived from `capabilities` ↔ `ACTIONS`; there is no single “available commands” endpoint. The client must maintain the display mapping (not authorization logic; the backend always decides).

## 3. Backend Gaps (for Desktop)

| UI module | Missing capability | Current Desktop behavior |
|---|---|---|
| Rooms | No room entity or room endpoints; only `room_id` (UUID) on devices and `?room_id=` filtering | Rooms page groups devices by `room_id` and displays `Room <short UUID>`; room names are unavailable |
| Command history | No `GET /commands` list with status/device filters and pagination | Show only commands sent in this session or remembered locally by `command_id`, using `GET /commands/{id}`; mark the limitation in the UI |
| Safety Center | No list of awaiting-confirmation commands or decision history | Show only commands known to the client; the full Safety Center remains blocked until `GET /commands?status=` exists |
| Activity | No API for reading `audit_log`; the table exists but is inaccessible | Empty state: unavailable on the backend |
| Telemetry history | No history endpoint; only the current `state` exists | Do not draw charts; show the current `state` |
| Dashboard | No aggregate endpoint for pending commands or events | Count values from `GET /devices` (total / online / offline / unknown); pending commands and recent events use an empty state |
| Automations | No module or API; an `automation` `CommandSource` value exists, but no engine | Information page: unsupported by the backend |
| Real-time | No WebSocket/SSE | Configurable polling interval (default 5–10 seconds, only for visible pages); poll dispatched/awaiting-confirmation commands more frequently |
| Device search and total | No `q=` and no total-count header | Filter the loaded page on the client; paginate with `limit/offset`; end of list when fewer than `limit` records are returned |
| Authorization | No `/me` and no login endpoint | Enter tokens manually; role is unknown, buttons remain available, and 403 responses display clear messages |
| AI Assistant | No API | Coming Soon / Disabled page |

## 4. Risks and Backend Notes (Desktop Does Not Fix Them)

1. **`InvalidStatusTransition` is not registered in `api/errors.py`** → confirming, rejecting, or cancelling a command in a terminal or unsuitable status returns **500**, not 409. Desktop should refresh the command before confirming/rejecting, show buttons only for `awaiting_confirmation`, and treat 500 as “the command state changed; refresh it.”
2. **Invalid `source`** (not `api|ai|automation`) → `CommandSource(dto.source)` raises `ValueError` and returns 500. Desktop always sends `"api"`.
3. **Confirming an expired command** returns **200** with `status=expired`. A 200 response is not success; Desktop must inspect the returned status.
4. **Reject** does not check expiry or require `awaiting_confirmation` in the service; transition-table protection is the only guard.
5. **Submitting an unknown slug** does not return 404: it creates a `rejected` command with `decision_reasons=["device_not_found"]` and the zero UUID. Display this as a safety rejection.
6. **No scheduler is found in `app.py`**: `expire_confirmations()`, `timeout_dispatched()`, and `redeliver_approved()` exist in the service but are never called. An unhandled `awaiting_confirmation` command may remain non-expired, and `dispatched` may remain non-timed-out. Desktop derives the display expiry from `expires_at`, but the server status remains the source of truth.
7. `FakeDispatcher`: a `dispatched` status is reached without real delivery; `acknowledged` appears only when a gateway calls `/ack`. Demo and production modes must state this explicitly (“waiting for device ACK”).
8. `GET /commands/{command_id}` accepts the client `command_id`, and so do `confirm/reject/ack`; `CommandDto.id` (the internal PK) is never used in these requests.
9. Idempotency: resubmitting the same `command_id` with the same slug/action/parameters/source returns the existing command rather than a duplicate. This is safe for timeout retries.
10. CORS is not configured on the backend. This is not critical for a Windows client but would be needed for a web build.

## 5. Impact on Requirements

- Requirements use uppercase statuses, but the wire uses lowercase. The Dart model must parse lowercase values and use `unknown` as a fallback for future statuses.
- Phase 4 (Commands & Safety) cannot be fully implemented without `GET /commands`.
- Phase 5 (Activity & Automations) is blocked by the backend: `GET /audit` and an automation module are required.
- Phase 6 (Real-time) becomes smart polling without WebSocket/SSE.
- The requirements mention Shared Preferences, but secrets must not be stored in plain text. Use `flutter_secure_storage` (Windows Credential Manager) for tokens and Shared Preferences only for URL and UI settings. This differs from the dependency list but follows the Settings and Security requirements.

## 6. Recommended Minimum Backend Contracts

| Need | Proposed contract |
|---|---|
| Command history | `GET /api/v1/commands?status=&device_id=&limit=&offset=` → `CommandDto[]` |
| Audit log | `GET /api/v1/audit?limit=&offset=&action=&since=` → `audit_log` records |
| Real-time | `GET /api/v1/events` (SSE) or `WS /api/v1/ws` with `CommandResolved`, `ConfirmationRequired`, `DeviceStateChanged`, `DeviceAvailabilityChanged`, and `EmergencyStopActivated` events |
| System state | `GET /api/v1/system/state` → `{"emergency_stop": bool}` (the client cannot currently determine whether emergency stop is active) |
| Current user | `GET /api/v1/me` → `{id, role}` |
| Rooms | `GET /api/v1/rooms` (if rooms become entities) |
| Fix 500s | Register `InvalidStatusTransition → 409` |
